## 二、世界标识、显示编号与排序改造

### 2.1 当前问题

现有前端使用“当前列表索引 + 1”渲染 `WORLD 01`，而列表按 `updated_at DESC` 排序。因此新导入、重新导入或刚编辑的世界总会移动到第一位并显示 `WORLD 01`。这个编号只是瞬时序号，不是真实世界 ID，也不能用于玩家识别、外部引用或审计。

### 2.2 四类标识严格分工

| 字段 | 用途 | 是否可变 | 是否对外显示 |
|---|---|---|---|
| `world_id` | 数据库内部世界记录 UUID；关联版本、快照、副本和审计 | 不可变 | 默认不显示 |
| `slug` | 世界包作者声明的稳定外部标识，如 `aelvion-ashen-crown` | 原则上不可变；改名需迁移映射 | 在导入详情和开发者视图显示 |
| `display_no` | 当前安装实例内的持久化展示编号 | 创建后不可变 | 显示为 `WORLD 01` 等 |
| `sort_order` | 管理员自定义列表顺序 | 可变 | 不直接显示 |

`world_content_version` 只表示世界内容版本，不承担身份职责；`snapshot_id` 标识副本使用的冻结规则版本，也不得替代 `world_id`。

### 2.3 分配与排序规则

1. 新建或“作为副本导入”时，在事务中分配 `display_no = max(display_no) + 1`。
2. 编辑名称、描述、封面、规则或更新时间时，保留原 `display_no`。
3. 同一 `slug` 的包执行“更新现有世界”时，保留 `world_id`、`display_no` 和已有副本，仅新增世界版本记录。
4. “复制世界”必须生成新的 `world_id`、新 `display_no` 和不冲突的 `slug`。
5. 删除后默认不复用 `display_no`，避免旧截图、日志和玩家称呼指向新世界。
6. 列表默认按 `sort_order ASC, display_no ASC`；没有手动排序值时令 `sort_order = display_no`。
7. `updated_at` 仅用于显示最近编辑时间，不再决定世界卡片编号或默认位置。
8. 管理员可拖拽调整 `sort_order`；拖拽不得修改 `display_no`、`slug` 或内部引用。

### 2.4 导入判定

- 内容哈希完全相同：提示“内容已存在”，不创建版本、不改编号。
- `slug` 命中且版本更高：进入更新预览，列出字段、实体和引用差异；确认后更新同一世界记录。
- `slug` 命中但版本相同、内容不同：视为冲突，禁止静默覆盖；提供取消、覆盖为新修订、另存副本三种明确操作。
- `slug` 未命中：创建新世界并分配新编号。
- 旧包没有合法 `slug`：按旧协议导入，但先生成迁移建议；不得再使用显示名称做长期匹配。
- 世界 `slug` 确需更名时，必须声明 `id_aliases`/迁移映射；所有引用校验通过后才可提交。

### 2.5 Schema 10 迁移

- 为世界表新增非空 `display_no`、`sort_order`；增加唯一索引和排序索引。
- 旧数据按 `created_at ASC, world_id ASC` 确定性回填编号，保证每次迁移结果一致。
- 将迁移前的列表位置、原 `slug`、新编号和世界 UUID 写入迁移报告。
- 迁移不修改世界内容版本、不触发副本更新、不刷新 `updated_at`。
- 前端、导出包、备份恢复和审计日志都必须读取持久化编号，禁止再次使用数组索引生成 `WORLD xx`。

## 三、v0.11.0 的通用化原则

### 3.1 核心原则

> 插件写死安全、确定、可验证、可回放的执行语法；世界包决定这些语法在当前世界中代表什么。

插件不再假定世界必然拥有职业、技能、生命、法力、敌我、元素、伤害、装备栏、回合冷却、D20 或“大成功/大失败”。这些都由世界包按需声明。

### 3.2 插件必须固定的内容

- 稳定 ID、作用域和类型化引用语法；
- 条件运算符、数据类型和空值语义；
- 操作白名单、事务、幂等、回滚和审计；
- 事件执行阶段和提交顺序；
- 权限、可见性、玩家控制权和内容安全底线；
- 最大递归深度、单次匹配数、操作数与资源消耗上限；
- 禁止执行代码、禁止读取未注册路径；
- 裁定凭证、世界规则快照和历史回放格式。

### 3.3 世界包自行决定的内容

- 实体、属性、标签、资源、能力和行动的名称与语义；
- 成长方式、克制/关系、效果组合、数值边界和叠加策略；
- 是否使用随机、使用什么随机方式、结果档位如何命名；
- 是否存在战斗、HP、装备槽、耐久、品质、冷却或伤害；
- 数据保存在哪个作用域以及何时允许带出副本；
- NPC 使用完整或简化 actor 结构。

### 3.4 已确认的去硬编码修正索引

| 原先偏窄的设计 | v0.11.0 修正 |
|---|---|
| `skills` 只指战斗技能 | 改为通用 `capabilities` |
| 每项技能必须有技能树 | `progression` 可省略，成长由转换操作组合 |
| 固定 HP/MP/行动点/冷却 | 统一为可选资源和使用限制 |
| 目标固定 self/ally/enemy | 使用通用实体选择器和世界标签 |
| 效果固定伤害/治疗/Buff | 使用受控状态变更操作 |
| 状态只指战斗 Buff/Debuff | 改为通用 `runtime_effects` |
| 装备必须有槽位/品质/耐久 | 对象只需定义、实例、关系和规则提供项 |
| 检定固定 D20 + 属性 vs DC | 改为世界声明的 `resolution_methods` |
| 结果固定大失败到大成功 | 世界声明稳定 `outcome_id` 和显示档位 |
| 条件只能读角色字段 | 读取注册作用域和类型化引用 |
| 触发只限使用技能/请求检定 | 使用标准阶段和世界领域事件 |
| AI 行动固定 `use_skill` | 改为通用 action intent，能力引用可选 |
| NPC 必须复制完整玩家卡 | 共用 actor 底层，允许简化复杂度 |
| 插件写死倍率上下限 | 世界声明玩法边界，插件只设技术安全边界 |
| 叠加只有取最高/加算/乘算 | 提供通用聚合策略和冲突拒绝 |
| 成长只能永久或仅副本 | 使用多级持久化作用域 |
| 每加功能就整体升级世界协议 | 核心版本与功能协议独立版本化 |
| WebUI 固定技能树 + 元素矩阵 | 根据模块动态显示通用和专用视图 |

## 四、协议与功能模块版本

### 4.1 顶层协议

```json
{
  "minimum_plugin_version": "0.11.0",
  "protocol": {
    "core_version": 5,
    "features": {
      "entity_registry": "1.0",
      "condition_engine": "1.0",
      "operation_engine": "1.0",
      "event_pipeline": "1.0",
      "resolution_receipt": "1.0",
      "capabilities": "1.0",
      "interaction_rules": "1.0"
    }
  },
  "required_features": [
    "capabilities@>=1.0",
    "interaction_rules@>=1.0"
  ]
}
```

### 4.2 加载原则

- `core_version: 5` 只表示能够声明模块化规则，不代表所有模块必填。
- 未列入 `required_features` 的模块不加载、不严格校验业务字段，也不在 WebUI 强制填写。
- 未声明能力或交互规则的世界自动视为关闭，不注入默认火冰关系、技能表或战斗资源。
- 插件版本不满足 `minimum_plugin_version` 或功能版本要求时，导入预检直接拒绝并给出缺失模块，不静默降级。
- 未知但声明为可安全保留的扩展字段在导入—编辑—导出链中不得丢失。

## 五、五层通用执行底座

### 5.1 Entity Registry

统一注册可被引用的实体、定义和实例，包括但不限于：

```text
actor / character / npc / object / location / organization / clue
capability / resource / stat / trait / relationship / runtime_effect
event / action_type / resolution_method / counter / story_flag / custom
```

引用采用类型化形式：

```text
capability:fireball
resource:inner_force
runtime_effect:wanted
location_route:north_gate
custom_tag:authority.royal
```

同一 ID 在所属注册表和世界作用域内唯一。显示名称可变，引用 ID 不随翻译、重命名或 UI 文案变化。世界包不得通过任意数据库路径访问数据。

### 5.2 Condition Engine

条件可读取注册过的作用域：

```text
actor / target / action / scene / world / session / party / location
object / relationship / event / runtime_effect / custom
```

支持 `all`、`any`、`not`、存在性、集合包含、类型比较、数值比较、引用比较、标签匹配和受控派生值。示例：

```json
{
  "compare": {
    "left": {"scope": "actor", "ref": "stat:power"},
    "operator": ">=",
    "right": {"scope": "target", "ref": "stat:agility"},
    "offset": 3
  }
}
```

`power`、`agility` 只是世界包 ID，插件不解释它们的自然语言含义。导入时校验引用，运行时在凭证中记录实际读取值。

### 5.3 Operation Engine

底层只提供受控状态变更，不以伤害或治疗为中心：

```text
modify_value / set_value / grant_reference / revoke_reference
add_tag / remove_tag / create_instance / end_instance
set_visibility / set_availability / advance_counter
modify_relationship / emit_event / request_resolution
add_narrative_constraint
```

伤害、治疗、封锁技能、获得线索、改变声望和关闭道路都是操作组合。每批操作必须带唯一 `operation_id`，以事务方式预检、应用、提交；重试不得重复扣资源、重复发放能力或重复产生效果。

### 5.4 Event Pipeline

统一阶段：

```text
before_event
validation
before_resolution
resolution
after_resolution
before_commit
after_commit
before_narration
```

世界包可以订阅标准事件，也可注册领域事件，如 `clue.discovered`、`ritual.completed`、`territory.entered`。自定义事件只能携带注册数据，不能携带或执行脚本。

### 5.5 Resolution Receipt

每次确定性裁定记录：

```json
{
  "receipt_id": "uuid",
  "operation_id": "uuid",
  "world_snapshot_id": "uuid",
  "event": {},
  "inputs": [],
  "condition_reads": [],
  "matched_rules": [],
  "steps": [],
  "outcome_id": "world_defined",
  "committed_changes": [],
  "narrative_projection": [],
  "created_at": "timestamp"
}
```

凭证用于玩家可读日志、后台调试、存档回放、重试幂等和争议复核。AI 只能读取经过可见性过滤的结果与叙事投影，不能改写机械结果。

### 5.6 推荐公开服务接口

接口名称可按实际代码风格调整，但职责边界必须保留：

```python
# 世界身份与版本
allocate_world_display_no(tx)
set_world_sort_order(world_id, sort_order, actor_id)
preview_world_import(package, import_mode)
commit_world_import(preview_id, actor_id)
create_world_snapshot(world_id, content_version)

# 注册、条件与规则
register_world_entities(world_snapshot)
resolve_ref(world_snapshot, typed_ref, scope)
evaluate_condition(condition, context)
match_event_rules(event, phase, context)

# 操作、裁定与凭证
plan_operations(event, matched_rules, context)
validate_operation_batch(operation_id, operations, context)
commit_operation_batch(operation_id, operations, context)
resolve_action_intent(intent, session_id, actor_id)
get_resolution_receipt(receipt_id, viewer_id)

# 能力与迁移
list_actor_capabilities(actor_ref, context)
grant_capability(actor_ref, capability_ref, source_ref, operation_id)
evaluate_capability_transitions(actor_ref, trigger_event)
preview_session_rule_upgrade(session_id, target_world_version)
clone_and_upgrade_session(session_id, migration_plan_id, actor_id)
```

扩展监听器只能观察 `after_commit` 的只读事件，或通过受控服务提交新意图；不得取得数据库连接、直接修改角色状态、伪造随机结果或绕过内容边界。

### 5.7 推荐持久化模型

Schema 10 至少需要覆盖以下逻辑实体；可按现有数据库风格合并物理表，但不能丢失职责：

| 逻辑实体 | 关键内容 |
|---|---|
| `world_feature_versions` | 世界版本启用的功能及协议版本 |
| `world_entity_registry` | 类型化实体 ID、显示名、定义版本、可见性和内容哈希 |
| `world_rule_revisions` | 能力、条件、操作、交互、裁定等冻结规则修订 |
| `world_snapshots` | 副本绑定的完整规则快照和来源版本 |
| `actor_capability_instances` | actor 实际拥有的能力、参数、来源、状态和定义版本 |
| `runtime_effect_instances` | 持续规则实例、作用域、持续条件、来源与层数 |
| `operation_commits` | `operation_id`、状态、输入哈希、提交结果和回滚信息 |
| `resolution_receipts` | 完整裁定凭证及玩家可见投影 |
| `migration_receipts` | 旧/新版本、ID 映射、授予/移除项、快照和确认人 |

大块世界规则可以 JSON 形式存储，但必须有内容哈希、Schema 校验、引用索引和不可变修订号。运行状态与定义数据必须分离，避免世界更新覆盖角色实例。

## 六、能力系统 `capabilities`

### 6.1 名称与适用范围

底层不使用只指战斗技能的 `skills`，统一称为 `capabilities`。它可表示武学、魔法、调查技巧、制作配方、黑客程序、身份权限、载具操作、被动天赋、血脉能力或剧情权能。

世界包自行注册 `capability_types`，插件不固定“主动/被动/法术/战技”等分类。

### 6.2 定义与角色实例分离

- `capability_definition`：世界规则中的能力模板；
- `capability_instance`：某角色在某规则快照下实际拥有的能力、参数、来源和状态；
- 角色实例冻结获取时的定义版本，世界更新不能静默改写已拥有能力；
- 同一来源重复授予通过 `grant_policy` 处理：忽略、刷新、叠层、提升参数或触发转换，且必须幂等。

### 6.3 成长不是强制技能树

`progression` 整块可省略。启用时可表达：

- 线性升级；
- 分支或技能图；
- 熟练度增长；
- 数值强化与追加效果；
- 形态变化；
- 装备期间临时获得；
- 两项能力组合生成新能力；
- 替换、保留、遗忘、降级、封印或异化；
- 剧情、DM、任务、物品、职业、属性或世界事件授予；
- 完全不成长。

“替换旧技能”“保留旧技能”“强化节点”只是通用操作的便捷模板，不是封闭枚举。

### 6.4 转换示例

```json
{
  "transition_id": "fireball_to_blast",
  "from": ["capability:fireball"],
  "when": {
    "all": [
      {"ref": "stat:fire_mastery", "operator": ">=", "value": 3},
      {"ref": "story_flag:completed_flame_trial", "operator": "==", "value": true}
    ]
  },
  "operations": [
    {"op": "set_availability", "target_ref": "capability:fireball", "value": false},
    {"op": "grant_reference", "target_ref": "capability:flame_blast"}
  ]
}
```

### 6.5 消耗、限制和目标全部可选

- 消耗引用世界自定义 `resources`，不使用固定 `mana_cost`；
- 冷却是 `usage_constraints` 的一种，可表达每回合、每幕、每天、特定地点、特定剧情阶段或计数器条件；
- 目标使用通用实体选择器，可指角色、对象、地点、组织、线索、任务、区域、场景或能力本身；
- “敌人/盟友”只是世界包标签，不是插件固定实体类型；
- 无目标、叙事型或自由行动不强制绑定能力。

### 6.6 AI 能力投影

剧情生成前只投影当前 actor 在当前快照、场景、资源和可见性条件下可用的能力实例。AI 输出通用行动意图，程序检查能力是否拥有、是否可用、目标是否合法、资源是否足够、规则是否匹配；验证失败不得提交机械变化，只返回可解释错误或重新生成。

## 七、可选通用交互规则 `interaction_rules`

### 7.1 定位修正

本功能不再称为固定“属性克制系统”。插件不规定火克冰、光克暗或力量克灵巧，只提供关系描述、条件匹配、效果结算和凭证留痕。世界包可以完全不声明或显式关闭：

```json
{"interaction_rules": {"enabled": false}}
```

### 7.2 可匹配对象

规则可以读取属性、能力、能力标签、行动标签、伤害标签、特征、种族、职业、身份、阵营、对象、状态、环境、地点、剧情标记、目标类型和自定义标签。它既能表达传统元素关系，也能表达：

- 力量类行动压制灵巧类防御；
- 机械单位不受精神干扰；
- 贵族身份在公开宫廷场景影响平民身份；
- 水下环境削弱某类火器；
- 法律知识有利于识破伪造文书；
- 圣物阻止亡灵恢复；
- 某项状态使一条路线不可用。

### 7.3 规则结构

```json
{
  "interaction_rules": {
    "enabled": true,
    "settings": {
      "conflict_strategy": "priority_then_stack",
      "max_matches_per_event": 10
    },
    "rules": [
      {
        "rule_id": "power_pressure",
        "mode": "hybrid",
        "enabled": true,
        "priority": 100,
        "triggers": [{"event": "action.requested", "phase": "before_resolution"}],
        "when": {"all": []},
        "effects": [],
        "stacking": {"group": "pressure", "strategy": "highest", "limit": 1}
      }
    ]
  }
}
```

### 7.4 执行模式与效果

| 模式 | 作用 |
|---|---|
| `mechanical` | 产生确定性数值、引用、状态或可用性变化 |
| `narrative` | 只向 AI 提供受控叙事关系，不修改机械数据 |
| `hybrid` | 同时产生机械结果和叙事约束 |

命中关系后可执行任何合法操作，例如修改检定、阈值、资源、计数器、持续效果、目标可用性或叙事提示。它不必产生伤害倍率。

### 7.5 叠加与安全

支持 `first`、`last`、`highest`、`lowest`、`sum`、`multiply`、`replace`、`unique`、`max_count`、`priority_only`、`deny_on_conflict` 等标准聚合策略。世界包定义玩法范围与数值策略；插件只限制 NaN、无穷值、过深递归、过多匹配和资源耗尽。反射结果默认带 `non_reflectable`，禁止再次反射形成无限循环。

## 八、其他通用模块

### 8.1 自定义资源 `resources`

资源可代表生命、内力、理智、弹药、声望、时间、筹码或调查进度。每项资源自行声明类型、范围、派生上限、可见性和持久化作用域。世界包不声明即不存在。

### 8.2 持续规则实例 `runtime_effects`

状态不再只表示战斗 Buff/Debuff。它可表示中毒、受伤、通缉、许可、掌握秘密、天气、区域封锁、外交豁免或剧情诅咒。持续单位支持 `turn`、`round`、`scene`、`chapter`、`session`、`world_time`、`until_condition`、`permanent`，展示名称可由世界包映射。

### 8.3 对象系统

对象只要求定义、实例、持有/激活关系和可提供的规则修改。槽位、重量、耐久、品质、套装、绑定和弹药均为可选模块。普通叙事世界可只用对象提供标签、权限或能力。

### 8.4 裁定方式 `resolution_methods`

不固定 D20、属性加值或 DC。世界包可声明 D20、D100、骰池、2D6、抽牌、无随机对比、成功数、资源竞价或纯叙事裁定。步骤只允许读取注册值、生成受控随机结果、比较、累计、应用修正和查询结果档位。

结果档位由世界包声明，如“完全成功”“付出代价后成功”“僵持”“局势恶化”。凭证保存稳定 `outcome_id`，前端按裁定方式生成玩家可读文本。

### 8.5 通用行动意图

AI 与玩家动作统一表示为：

```json
{
  "actor_ref": "character:xxx",
  "action_type": "world_defined_action",
  "capability_ref": "capability:optional",
  "targets": [],
  "parameters": {},
  "declared_intent": "希望实现的目标"
}
```

世界包注册 `attack`、`persuade`、`investigate`、`travel`、`craft`、`trade`、`command`、`perform_ritual` 或其他行动类型。`freeform` 允许不绑定能力的普通叙事行动。

### 8.6 Actor 与 NPC

玩家和 NPC 都属于 `actor`，共享引用、资源、能力、状态和规则接口，但复杂度可不同。杂兵可只保存威胁等级、标签、少量能力和简化状态；重要 NPC 可使用完整结构。NPC 模板不得强迫所有 NPC 拥有玩家式角色卡。

### 8.7 数据持久化作用域

支持：

```text
global_character / world_character / campaign / session / scene / temporary
```

能力和其他变化默认写入世界包声明的作用域。不同世界之间默认不互通；跨世界携带必须经过显式映射和玩家确认。副本结束后的永久写回采用单独结算凭证，不直接污染基础角色卡。

## 九、统一调用流程

1. 接收玩家、DM、AI 或系统产生的行动意图。
2. 解析 `actor_ref`、行动类型、能力和目标；加载副本冻结的世界快照。
3. Entity Registry 验证所有引用和可见性。
4. Event Pipeline 进入 `validation`；检查控制权、能力解锁、资源、目标、边界和用法限制。
5. Condition Engine 读取已注册值，匹配能力规则、交互规则、对象和持续效果。
6. `resolution_methods` 执行确定性/随机裁定；随机数由插件产生，模型不能控制。
7. Operation Engine 构建操作批次，在 `before_commit` 再次校验幂等、权限和数值策略。
8. 事务提交资源、能力、状态、关系、计数器和世界变化；失败则整体回滚。
9. 生成 Resolution Receipt 和面向玩家的简化日志。
10. 仅把当前相关结果、公开规则来源和叙事约束投影给文字模型。
11. 模型生成叙事；叙事不能反向覆盖已提交机械事实。

## 十、WebUI 改造

### 10.1 世界列表

- 卡片读取持久化 `display_no`；
- 默认顺序不再受编辑时间影响；
- 支持拖拽排序并仅修改 `sort_order`；
- 开发者详情显示 `world_id`、`slug`、内容版本、协议和功能模块；
- 导入冲突页明确区分更新、另存副本和取消。

### 10.2 模块化世界编辑器

根据已启用功能动态显示：

- 实体与引用注册；
- 能力定义、授予规则、成长关系和角色解锁预览；
- 资源、对象和持续效果；
- 交互规则、条件、优先级、叠加与冲突提示；
- 裁定方式、结果档位和数值策略；
- 世界事件、行动类型和持久化作用域；
- 知识/内容边界及 v4 通用预设。

“技能树”和“关系矩阵”仅在数据适合时作为专用视图。复杂交互规则必须保留列表/规则编辑器，矩阵不能丢失条件、优先级、模式和效果。

### 10.3 统一效果编辑器

作者从受控操作或语义模板中选择，再填写参数；不得输入可执行代码。编辑器应实时显示引用存在性、类型、写入作用域、冲突、潜在循环和操作数量。

### 10.4 规则模拟器

输入 actor、行动/能力、目标和场景，展示：

```text

命中的条件和交互规则
随机或对比步骤
叠加与优先级
拟提交操作
最终结果与 outcome_id
每一步规则来源
完整但未提交的裁定凭证
```

默认是只读 dry-run，不修改真实存档。复杂世界包未通过模拟器与预检不得发布。

### 10.5 角色与副本页面

- 显示能力定义版本、实例来源、解锁/封印状态和可用条件；
- 显示资源、持续效果、对象提供的能力和作用域；
- 显示迁移凭证、世界快照和最近裁定凭证；
- DM 页面继续遵守 v0.10.0 主持状态机，并只显示 DM 有权限查看的私密规则。

## 十四、兼容与迁移

### 14.1 世界协议矩阵

| 世界协议 | 处理方式 |
|---|---|
| v2/v3 | 使用旧建卡与旧规则链；只补数据库展示编号，不改世界内容 |
| v4 | 使用通用预设、知识与内容边界；新规则模块默认关闭 |
| v5 | 按 `required_features` 加载声明模块；未启用模块不参与运行 |

### 14.2 旧角色卡

- 不直接重写历史角色卡。
- 首次进入明确启用新模块的 v5 新副本时，根据角色预设和世界授予规则生成能力实例。
- 记录来源角色卡版本、授予能力、对应预设、世界快照和迁移操作 ID。
- 重复进入不得再次授予；失败整体回滚。

### 14.3 旧存档

- 默认继续旧引擎和冻结快照；
- 不把新能力表写入旧存档，不根据新版世界包回算已发生裁定；
- 只有“克隆并升级”产生新存档分支；原存档保持可读可恢复。

### 14.4 世界实体 ID 变化

- 显示名称变化不需要迁移；
- 稳定 ID 变化必须提供一对一或明确的一对多迁移映射；
- 删除仍被角色、对象、NPC、状态或存档引用的 ID 时，导入预检直接拒绝，除非同时提供替代/终止操作；
- 映射完成后保留别名只读解析期，所有新写入统一使用新 ID。

## 十五、风险与强制防护

| 风险 | 防护 |
|---|---|
| 能力图循环依赖 | 导入时进行有向图循环检测；允许世界明确声明的可逆状态转换，但必须有终止条件 |
| 引用不存在或类型不匹配 | 预检拒绝，禁止运行时静默忽略 |
| 多规则数值爆炸 | 世界数值策略、叠加组、优先级和技术安全边界共同限制 |
| 反射无限递归 | 反射派生事件不可再次反射 |
| AI 使用未解锁能力 | 最小能力投影 + 提交前程序校验 |
| 世界更新造成规则漂移 | 副本冻结快照，能力实例保存定义版本 |
| 以名称覆盖错误对象 | 所有机械引用使用稳定 ID，名称仅显示 |
| 任意公式或脚本风险 | 白名单表达式和操作，禁止代码执行与任意字段路径 |
| 重试重复扣除/发放 | `operation_id` 幂等、唯一约束和事务提交 |
| 永久成长污染基础角色卡 | 作用域隔离，副本结算后单独确认写回 |
| 模型上下文膨胀 | 只投影当前 actor、目标、场景和命中规则 |
| 显示编号再次漂移 | 前端禁止数组索引编号；数据库唯一约束与回归测试 |
| 同 slug 冲突覆盖 | 导入差异预览与明确选择，禁止静默覆盖 |
| 规则数量耗尽资源 | 每事件匹配、条件深度、操作数、派生事件数设技术上限 |

## 十七、产品规则默认决策

为避免开发再次停在未确认项，v0.11.0 采用以下通用默认值，世界包可在安全范围内覆盖：

1. 成长默认写入 `campaign`，永久带出需单独结算确认。
2. 不同世界的能力默认不互通；跨世界必须显式映射。
3. HP、MP、行动点和回合冷却都不是必选系统。
4. 数值效果与无 HP 的叙事效果均可存在，必须标明 mechanical/narrative/hybrid。
5. 升级节点可由玩家选择、剧情、DM 或世界规则授予，具体由转换规则声明。
6. 分支重置默认禁止；世界包可用合法条件和操作定义重置代价。
7. 重复授予默认幂等忽略；其他处理必须显式声明 `grant_policy`。
8. 多条关系默认按优先级后按组聚合；具体策略由规则组声明。
9. 装备槽、耐久、品质和套装全部可选。
10. NPC 与玩家共享底层结构，但允许不同复杂度模板。

## 十八、完整验收清单

### 18.1 版本与打包

- 插件、manifest、README、配置、WebUI、模板和 CHANGELOG 全部为 0.11.0 对应版本；
- 作者为 Ghostberry，更新日志不出现作者名修正条目；
- 最终 ZIP 解压后重复执行编译、JSON、模板和测试检查。

### 18.2 世界编号与导入

- 编辑任意世界后 `WORLD xx` 不变；
- 导入新世界只为新世界分配新编号，不重排旧编号；
- 同 slug 更新保留编号，另存副本获得新编号；
- 删除后编号不复用；拖拽只改变顺序；
- Schema 9 升级回填稳定且可重复验证；
- 备份导出/恢复后 `world_id`、`slug`、`display_no` 和 `sort_order` 一致。

### 18.3 通用协议

- v2/v3/v4 世界包行为不变；v5 可只启用单个功能模块；
- 缺失必需功能、非法引用、循环依赖和错误类型在导入预检中准确报错；
- 未启用能力/交互规则的世界不出现空白必填项，不参与相关结算；
- 未知安全扩展字段导入—编辑—导出不丢失。

### 18.4 能力与规则

- 线性、分支、组合、替换、保留、封印和无成长能力均可表达；
- 资源、目标、限制和效果全部可以省略或世界自定义；
- AI 不能使用未解锁、资源不足、目标非法或当前不可用的能力；
- 力量/灵巧、身份、环境、对象、元素等关系均能用同一接口表达；
- narrative 规则不误改机械数据，mechanical 结果不被 AI 叙事覆盖；
- 规则冲突、叠加、反射、数值边界和幂等重试均有自动测试。

### 18.5 快照、迁移与存档

- 世界更新不改变运行副本和历史凭证；
- 旧角色首次进入 v5 新副本只迁移一次；
- 迁移失败不产生半成品能力或资源；
- 克隆升级生成新快照、新凭证并保留原存档；
- 显示名称更改不破坏引用，稳定 ID 更改必须经过映射。

### 18.6 WebUI 与模拟器

## 二十、最终实施结论

v0.11.0 不是在 v0.10.0 上增加一个“技能树”和一张“元素克制表”，而是完成一次规则执行层升级：模型负责理解行动与生成叙事，插件负责引用、校验、随机、匹配、结算、事务、凭证和快照，世界包通过安全的声明式接口决定具体世界语义。

世界编号修复、能力变更、关系匹配、资源、对象、状态、裁定、NPC 和未来的线索、声望、身份权限、召唤物或天赋都统一复用同一底座；不需要这些功能的世界包可以完全不启用。这样既保留 v0.10.0 已有的建卡、主持和边界能力，也避免 v0.11.0 再次形成只适用于传统 RPG 的硬编码分支。
